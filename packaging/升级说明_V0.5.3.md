# V0.5.3 升级说明（Windows 服务端 / 桌面版）

本版本修复三个现场问题：**管理页入口消失**、**导入工作日志时 AI 智能整理不再出现**、**换运行方式后账号与交接班记录像是被清空**。

升级不会重置任何个人密码，不会删除任何历史数据。会新增一个数据库列（`staff.is_admin`），迁移前自动创建一致备份。

---

## 一、升级前必做：记录数据目录

数据目录此前会随运行方式变化（桌面模式用 `runtime`，服务模式用 `runtime-server`），换一种启动方式就可能指向空目录并生成全新空库。**升级前先记录当前数据库的真实位置和大小**，升级后核对是否一致。

打包版程序里没有 Python 环境，用下面两个入口确认（两者看到的是同一份数据）：

1. **服务器控制器** → 配置页的“正式数据目录”就是当前数据根；工具区“打开完整备份目录”可直接看到备份产物。
2. **浏览器访问** `http://127.0.0.1:8765/api/health`，返回中的 `data_root`、`data_root_report` 给出数据根、数据库路径、数据库大小、是否已显式固定、是否还存在带数据的历史目录。

**请把这两处的输出保存下来**（截图或复制文本），它是判断“数据有没有丢”的唯一客观依据。

源码部署（有 `.venv`）还可以用脚本查看与接管：

```powershell
.\.venv\Scripts\python.exe backend\scripts\data_location.py
```

要彻底避免以后再漂移，在服务器控制器里把“正式数据目录”固定到一个不会被程序覆盖的位置（仅允许本机固定磁盘，不接受网络共享）。

升级后本版本会在启动时自动接管历史数据目录，规则是：

- 仅当当前数据根**没有数据库**、且历史候选目录**唯一**时才接管；
- **只复制，不移动，不删除**原目录；
- 复制后校验数据库完整性，失败则整体回滚，原目录保持完整；
- 候选多于一个时**不自动选择**，控制器日志会告警，需人工确认哪一份才是正式数据。

## 二、升级步骤

1. 在管理页创建一份完整备份。管理员进不去时先跳到第三节恢复入口。
2. 用服务器控制器**安全停止**服务器，再关闭控制器。
3. 把新版本完整解压到一个**新目录**（旧版本目录保留，便于回退）。
4. 从新版本目录运行服务器控制器并启动服务器。
5. 打开页面，确认右上角显示 `V0.5.3`；进入管理页确认顶部"当前服务版本"也是 `0.5.3`。
6. 重新查看 `http://127.0.0.1:8765/api/health`，与升级前保存的输出对比数据库大小与路径。

版本不一致说明前端产物或后端没有一起更新，请确认解压的是完整新包。

## 三、找回"系统管理"入口

### 原因

管理员身份此前**只**由 `.env` 里的 `JX_ADMIN_NAMES` 决定。该项为空时全部人员都变成操作员，姓名菜单里"系统管理"直接消失，所有管理接口返回 403，而且没有任何报错。

### 现在的行为

- 管理员标记保存在数据库 `staff.is_admin` 中，数据库是权威来源。改配置、重装、换机器都不会再把人降权。
- `JX_ADMIN_NAMES` 仍在每次启动时提升名单中的人员，作为重装时的保底。
- 启动时若发现**没有任何管理员**，按 `JX_DEFAULT_ADMIN_NAMES`（默认片区负责人）兜底提升一次并写显著告警，避免管理页与备份恢复入口同时锁死。该项置空即关闭兜底。
- 完全没有管理员时不再静默：写严重告警日志，`/api/health` 返回 `admin_configured=false`。
- 非管理员在姓名菜单看到**禁用项**"系统管理（需管理员权限）"及说明，不再是菜单项凭空消失。

### 操作步骤

1. 启动服务器后查看控制器日志，确认没有“当前没有任何管理员账号”的严重告警。
2. 用兜底提升的账号登录，姓名菜单应出现可点击的“系统管理”。
3. 进入管理页 → 人员账号，把实际需要管理的人**逐个点“设为管理员”**。被设置的人需**重新登录**才能看到入口。
4. 在服务器控制器“管理员姓名（逗号分隔）”里也写上这些人，作为重装时的保底。
5. 已经至少有一个管理员后，如不希望保留兜底账号，在服务器环境变量里把 `JX_DEFAULT_ADMIN_NAMES` 置空。

### 管理页打不开时的恢复入口

**打包版（无 Python 环境）**：打开服务器控制器 → 配置页“管理员姓名（逗号分隔）”填入准确姓名（必须与启用人员完全一致，中文逗号会自动转换）→ 保存 → 重启服务器。启动时这些姓名会被提升为管理员，登录后即可看到“系统管理”。

控制器打不开或保存失败时，先访问 `http://127.0.0.1:8765/api/health` 确认服务在跑、`admin_configured` 是否为 `false`；再确认控制器里的“正式数据目录”指向的是带数据的那个目录（指错目录是最常见的原因）。

**源码部署（有 `.venv`）**：可直接用命令行恢复脚本：

```powershell
.\.venv\Scripts\python.exe backend\scripts\manage_admin.py --list
.\.venv\Scripts\python.exe backend\scripts\manage_admin.py --grant "准确姓名"
.\.venv\Scripts\python.exe backend\scripts\manage_admin.py --revoke "准确姓名"
```

- `--list` 会先迁移旧结构，因此**升级后尚未启动服务也能正常列出**；同时输出数据目录与数据库路径，便于确认操作的是不是正式库。
- 姓名必须与启用人员完全一致；存在同名启用人员时脚本会直接报错退出，不会自行猜测。
- `--revoke` 不会取消最后一个管理员；被取消的人在线登录立即失效。
- 数据库文件不存在时脚本**直接报错退出，且不会新建空库**。这是刻意设计：就地新建空库会让启动接管逻辑误判“已有数据”，把可恢复的情况变成永久丢失。此时先确认数据目录是否指错。

### 守卫规则（管理页与命令行一致）

| 操作 | 结果 |
| --- | --- |
| 取消最后一个管理员 | 拒绝，提示必须保留至少一个 |
| 停用最后一个启用状态的管理员 | 拒绝 |
| 取消 `JX_ADMIN_NAMES` 中指定人员的管理员 | 拒绝，需先改服务器配置并重启 |
| 修改自己的账号 | 拒绝，需由另一位管理员操作 |

## 四、重新开启 AI 智能整理

### 原因

`AI_MODE=mock` 且未填 API Key 时，后端返回"未启用"状态，而页面此前没有处理这个状态，显示成**红色错误**，看起来像功能被删除。加上 AI 配置入口在管理页内，随上一个问题一起消失，就没有任何地方能重新打开它。

**功能本身从未被移除。**

### 操作步骤

1. 打开服务端控制器 → 填写阿里云百炼 API Key → 保存并重启服务器。
   （源码部署则在 `.env` 中设 `AI_MODE=auto`、填写 `QWEN_API_KEY`。）
2. 管理页 → "Qwen 智能整理"卡片 → 点"测试 AI 连接"，确认识别为 Qwen。
3. 重新导入一次工作日志，预览区应显示 AI 整理结果。

`AI_MODE` 现在默认 `auto`：填了 Key 就用真实模型，没填就回落本地规则解析，不需要显式声明。`QWEN_BASE_URL` 与 `QWEN_MODEL` 留空即用官方默认值。

### 验收

- 管理页 AI 卡片"运行模式"为 `Qwen 智能整理`，显示模型名与 `****xxxx` 形式的 Key 尾号，且**不出现**"配置要求…（未生效）"这一行。
- 若刻意不填 Key：导入预览区显示灰色"AI 智能整理未启用，已用本地规则解析"，**不是红色错误**，解析结果完整可用。

## 五、版本号说明

版本号此前分散在多处（控制器硬编码 0.4.1、页面文字 V0.5.1/V0.5.2、EXE 属性 0.3.0 与 0.4.1），同一次安装会显示多个不同版本。现已统一到程序目录下的 `VERSION` 文件：控制器、后端、页面右上角、管理页、EXE 属性和发布清单全部以它为准。

页面右上角版本号改为读取后端实际运行版本，因此**它显示的就是真正在跑的版本**，不再是写死的文字。

发布包目录名也改为版本驱动。这一点影响升级判定：升级流程是从解压后的**目录名**识别版本的，沿用旧名会让新包自报为旧版本、被当成降级。
