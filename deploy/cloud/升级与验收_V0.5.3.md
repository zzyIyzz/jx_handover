# V0.5.3 升级与验收

本版本修复三个现场问题：**管理页入口消失**、**导入工作日志时 AI 智能整理不再出现**、**换运行方式后账号与交接班记录像是被清空**。三者都不是页面缓存，升级后需要按下面的顺序验收。

公网入口仍是 `https://你的公网IP:1215`，内部服务仍是 `127.0.0.1:8765`。
本次会新增一个数据库列（`staff.is_admin`），迁移前自动创建一致备份；不重置任何个人密码。

---

## 升级前必做：确认数据目录

数据目录此前会随运行方式变化（`runtime` / `runtime-server` / `/www/jx-handover/data`），换一种启动方式就可能指向空目录并生成全新空库。**升级前先记录当前数据库的真实位置**，升级后核对是否一致。

```bash
# Docker 部署：宿主机数据目录
ls -lh /www/jx-handover/data/data/handover.db

# systemd / 宝塔 Python 部署：在项目目录执行
cd /www/jx-handover/app
python3 backend/scripts/data_location.py
```

`data_location.py` 会输出当前数据根、数据库大小、是否为显式配置，以及是否还存在含数据的历史目录。**请把这段输出保存下来**，它是判断"数据有没有丢"的唯一客观依据。

升级后本版本会在启动时自动接管历史数据目录，规则是：

- 仅当当前数据根**没有数据库**、且历史候选目录**唯一**时才接管；
- **只复制，不移动，不删除**原目录；
- 复制后用 `PRAGMA quick_check` 校验，失败则整体回滚，原目录保持完整；
- 候选多于一个时**不自动选择**，日志会提示用 `data_location.py --adopt <目录>` 显式指定。

要彻底避免以后再出现目录漂移，在服务器 `.env` 中显式固定（Docker 部署已在 compose 中固定为 `/var/lib/jx-handover`，无需改动）：

```dotenv
JX_HANDOVER_DATA_DIR=/www/jx-handover/data
```

## 升级步骤

### Docker 部署

先在管理页创建一份完整备份。管理员进不去时，在原 Compose 目录执行：

```bash
cd /www/jx-handover/app/deploy/cloud
docker compose exec -T app python -m scripts.cloud_backup create
```

确认备份成功后更新代码（若使用了其他项目路径，替换下列路径）：

```bash
cd /www/jx-handover/app
git status --short
git fetch origin
git pull --ff-only origin main
bash deploy/cloud/scripts/deploy.sh
```

`deploy.sh` 会重新构建镜像。**必须重新构建**：前端产物打包在镜像里，只拉源码不重建，页面仍是旧的。
镜像标签已改为 `jx-handover:current`，不再需要手工改 compose 里的版本号。

### systemd / 宝塔 Python 部署

先确认服务名、项目目录、虚拟环境和正式数据目录，不要另开一套 Docker 服务同时访问同一个数据库。

```bash
systemctl list-units --type=service --all --no-pager | grep -Ei 'jx|handover'
```

在原项目目录拉取同一分支，用原虚拟环境安装 `backend/requirements.txt`，在 `frontend` 目录执行 `npm ci` 与 `npm run build`（`npm run build` 现在会先跑类型检查），然后重启**原服务**。

### 两种部署都要检查

如果服务器 `.env` 里手工设置过 `JX_APP_VERSION`，请**删除该行**。版本号现在统一由仓库根 `VERSION` 文件提供，保留旧覆盖值会让页面继续显示过期版本。

## 问题一：找回"系统管理"入口

### 根因

管理员身份此前**只**由环境变量 `JX_ADMIN_NAMES` 决定。该变量为空时，全部人员都变成操作员，前端隐藏"系统管理"菜单，所有 `/api/admin/*` 接口返回 403。配置检查只在 `cloud` 模式执行，`server` 模式静默通过，所以没有任何报错。

### 现在的行为

- 管理员以**配置名单为权威**：`JX_ADMIN_NAMES` 非空时以它为准，为空时以 `JX_DEFAULT_ADMIN_NAMES`（本版本代码默认 `周智源`）为准。
- 每次启动执行**权威同步**：提升名单内的启用人员、回收名单外人员的管理员标记（其旧登录会话同时失效），使部署收敛到"恰好名单里的这些人"。因此服务器 `jx-update` 重启后即自动对齐，无需手工改数据库；标记同时持久化在 `staff.is_admin`。
- **防锁死**：名单匹配不到任何启用人员时（例如姓名打错）跳过回收，绝不清空最后一个管理员。`JX_DEFAULT_ADMIN_NAMES=` 置空即关闭兜底名单。
- 完全没有管理员时不再静默：写 `critical` 日志，`/api/health` 公开 `admin_configured=false` 与恢复提示。
- 非管理员在右上角姓名菜单看到**禁用项**"系统管理（需管理员权限）"及说明，不再是菜单项凭空消失。

### 验收步骤

1. 重启服务后查看日志，确认没有出现"当前没有任何管理员账号"的 `critical` 告警；若之前由旧兜底名单提升过 `刘学森`，应看到"启动同步：管理员以配置名单为准（周智源），已回收名单外人员 刘学森 的管理员权限"这类告警。
2. 访问 `/api/health`，确认 `admin_configured` 为 `true`、`version` 为 `0.5.3`。
3. 用 `周智源` 登录，右上角姓名菜单应出现可点击的"系统管理"；用其他账号登录则看不到该入口（或显示为禁用项）。
4. 如需固定为其他或多个管理员，在服务器 `.env` 写 `JX_ADMIN_NAMES=姓名1,姓名2`，重启后系统对齐到这份名单。
5. 建议 `JX_ADMIN_NAMES` 与 `JX_DEFAULT_ADMIN_NAMES` 都填 `周智源`（仓库两份 `.env` 模板已如此），避免重装后回落到非预期名单。

### 管理员彻底进不去时的本机恢复

在服务器本机（或容器内）执行。这是管理页打不开时的唯一入口：

```bash
# Docker
cd /www/jx-handover/app/deploy/cloud
docker compose exec -T app python -m scripts.manage_admin --list
docker compose exec -T app python -m scripts.manage_admin --grant '准确姓名'

# systemd / 宝塔：在项目目录用原虚拟环境
python3 backend/scripts/manage_admin.py --list
python3 backend/scripts/manage_admin.py --grant '准确姓名'
```

- `--list` 会先迁移旧结构，因此**升级后尚未重启服务也能正常列出**；同时输出数据目录与数据库路径，便于确认操作的是不是正式库。
- 姓名必须与启用人员完全一致；存在同名启用人员时脚本拒绝操作。
- `--revoke` 不会取消最后一个管理员；被取消的人在线登录立即失效。
- 数据库文件不存在时脚本**拒绝执行且不新建空库**。这是刻意设计：就地新建空库会让启动接管逻辑误判"已有数据"，把可恢复的情况变成永久丢失。此时请先用 `data_location.py` 确认数据目录是否指错。

### 守卫规则（管理页与脚本一致）

| 操作 | 结果 |
| --- | --- |
| 取消最后一个管理员 | 拒绝，提示必须保留至少一个 |
| 停用最后一个启用状态的管理员 | 拒绝 |
| 取消配置名单（`JX_ADMIN_NAMES`，缺省 `JX_DEFAULT_ADMIN_NAMES`）中指定人员的管理员 | 拒绝，需先改服务器配置并重启 |
| 修改自己的账号 | 拒绝，需由另一位管理员操作 |

## 问题二：重新开启 AI 智能整理

### 根因

两层原因叠加：

1. `AI_MODE=mock` 且未配置 API Key 时，后端返回 `status="disabled"`，而前端没有处理这个状态，落到默认分支显示成**红色错误**，看起来像功能被删除；
2. AI 配置与"测试 AI 连接"都在管理员门禁内，随问题一一起消失，所以没有任何地方能重新打开它。

**功能本身从未被移除。**

### 现在的行为

- `AI_MODE` 默认 `auto`：配置了 `QWEN_API_KEY` 就用真实模型，没配置就回落本地规则解析，不需要显式声明。
- `QWEN_BASE_URL` 与 `QWEN_MODEL` 为空时回落官方默认值。
- `disabled` 在前端显示为**中性灰色提示**，并写明“功能没有丢失”以及到管理页开启的路径。
- 管理页 AI 卡片“运行模式”显示实际生效的解析方式（`Qwen 智能整理` 或 `本地确定性规则`）；当配置的 `AI_MODE` 未生效时，额外显示一行“配置要求：AI_MODE=xxx（未生效）”。

### 开启步骤

在服务器 `.env` 中填入（Key 只保存在服务器，不进 Git、不进镜像、不进前端）：

```dotenv
AI_MODE=auto
QWEN_API_KEY=sk-你的实际密钥
# 下面两项留空即用官方默认值
QWEN_BASE_URL=
QWEN_MODEL=
```

重启服务后：管理页 → AI 配置 → 点击"测试 AI 连接"确认连通 → 重新导入一次工作日志，预览区应显示 AI 整理结果。

### 验收步骤

1. 管理页 AI 卡片“运行模式”应为 `Qwen 智能整理`，并显示模型名与 `****xxxx` 形式的 Key 尾号；不应出现“配置要求…（未生效）”这一行。
2. "测试 AI 连接"返回成功。
3. 导入工作日志，预览区显示 AI 已整理条数。
4. 若刻意不配 Key：预览区应显示灰色"AI 智能整理未启用，已用本地规则解析"，**不是红色错误**，解析结果完整可用。

## 问题三：核对数据没有丢

1. 升级后重新执行 `data_location.py`（或 Docker 内 `python -m scripts.data_location`），与升级前保存的输出对比数据库大小。
2. 管理页顶部“管理员与数据目录”卡片显示数据根路径与管理员名单。
3. 管理页 → 服务器健康，看“账号信息与交接班记录的存放位置”区块，确认：
   - 右上角标签为“已显式固定”（若为“程序默认目录”，建议按上文写入 `JX_HANDOVER_DATA_DIR` 固定）；
   - “已从旧目录接管”为空，或指向你认可的历史目录；
   - “旧目录仍有数据（未使用）”不出现。若出现，说明还有一个历史目录带着数据，页面会持续黄色告警，需人工确认哪一份才是正式数据。
4. 登录后检查历史班次与人员账号是否齐全。
5. `/api/health`（非云端模式）包含 `data_root_report`；云端模式刻意不公开路径，需通过管理员诊断接口查看。

## 版本号核对

版本号此前分散在四处（`server_config.py` 硬编码 0.4.1、前端页面文字 V0.5.1/V0.5.2、EXE 版本资源 0.3.0 与 0.4.1、Docker 镜像标签 0.5.2），同一次安装会显示多个不同版本。现已统一到仓库根 `VERSION` 文件。

升级后这四处的版本必须一致：

| 位置 | 查看方式 |
| --- | --- |
| 后端 | `/api/health` 的 `version` |
| 页面 | 右上角 `V0.5.3`（鼠标悬停显示后端实际版本） |
| 管理页 | 顶部"当前服务版本" |
| 镜像/EXE | `docker images` 标签已改为 `current`；Windows EXE 属性由构建自动生成 |

不一致说明后端未重启或前端未重新构建。
