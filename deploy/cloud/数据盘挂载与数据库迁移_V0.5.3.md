# 数据盘挂载与数据库迁移方案 V0.5.3

把交接班系统的运行数据（含唯一的 SQLite 正式库）从系统盘迁到独立数据盘
`/dev/vda3`（ESSD），目标目录示例 `/data/jx-handover/data`。

> 铁律不变：SQLite 必须在 **ECS 本地固定磁盘**，不能放 OSS / NAS / SMB /
> WebDAV / 同步盘 / FUSE 挂载点；所有浏览器必须连同一个后端实例。数据盘只是
> 换一块本地盘，不是网络存储。

本方案同时给出两种运行形态的步骤，按你服务器实际用的那种执行：
- **形态 A：systemd 直跑 uvicorn**（你们当前生产：`jx-handover.service`，
  代码在 `/www/wwwroot/jx_handover`，数据在其下的 `runtime-server`）
- **形态 B：Docker Compose**（仓库 `deploy/cloud` 云端档案，数据由
  `JX_HOST_DATA_DIR` 绑定进容器）

---

## 〇、数据盘必须完整保存什么（数据清单）

应用把**所有可变数据**都写在同一个数据根 `USER_DATA_ROOT` 下（由
`JX_HANDOVER_DATA_DIR` / 容器内 `/var/lib/jx-handover` 决定）。只要这个根落在
数据盘上，下面三类关键数据就全部随盘持久化，重启/升级/容器重建都不丢：

| 数据根子目录 | 内容 | 对应你的三类要求 |
|---|---|---|
| `data/handover.db` | 唯一 SQLite 正式库：`staff`（含 Argon2id `password_hash`、`session_version`、`is_admin`）、批次 `import_jobs`、事项 `handover_items`、月度计划、外委考核、导入预览、文档快照 `document_snapshots`、审计 `audit_events` | ①人员账号体系 ②交接班业务记录（批次/事项/审核/审计） |
| `generated/` | 生成的交接班 Word 文件本体（`document_snapshots.docx_path` 指向此处） | ③Word 文档本体 |
| `imports/` | 每个批次归档的原始 Excel 源文件（按 `batch_id` 分目录） | ②业务记录的原始凭证 |
| `snapshots/` | 完整业务备份 ZIP、迁移前自动备份 `database_backups/`、OSS 同步状态 | 备份与迁移安全网 |
| `logs/` | 应用运行日志 | 运维排障 |

**代码/模板不在数据盘**：Word 模板 `handover_v1.docx`、标准导入模板、前端
`dist` 都随代码仓库走（升级时更新），不是用户数据，无需迁移。

> 结论：数据盘挂载点 = 数据根，一块盘即可完整承载①②③。迁移本质就是
> **把数据根从系统盘整体复制到数据盘**，不涉及任何数据格式转换。

### 会话为何能跨重启不丢

登录令牌是**无状态签名令牌**（存在浏览器 Cookie），服务端不保存会话表；
失效控制靠 `staff.session_version`（在库里）。因此重启/重建后旧登录仍有效，
**前提是 `JX_SESSION_SECRET` 必须固定写在 `.env` 里**——它一变，所有已发令牌
立即失效（这是安全设计，不是数据丢失）。迁移时务必把 `.env` 的
`JX_SESSION_SECRET` 一并保留。

## 〇.5、版本兼容性保障（v0.5.3 及以后）

数据库结构演进由 `backend/app/migrations.py` 统一管理，机制对历史数据是
**只增不改、绝不破坏**，任何新版本都能正确读取旧库：

1. **纯增量迁移**：升级只执行 `ALTER TABLE ... ADD COLUMN`（且先检测列是否
   已存在）和 `Base.metadata.create_all`（只建缺失的表/索引）。源码注释明确
   “never rewrites document snapshots; only missing columns/tables are added”，
   **没有任何 DROP / DELETE / 改列类型**。
2. **新列一律带 `NOT NULL DEFAULT`**：旧行自动获得合法默认值，不会因加列而
   变成非法数据。
3. **迁移前自动安全备份**：一旦判定需要迁移，先用 SQLite 在线备份 API
   （含已提交的 WAL 页）生成 `snapshots/database_backups/handover_before_migration_*.db`，
   并 `PRAGMA quick_check`；校验不通过就**中止迁移**，绝不带病升级。
4. **幂等 + 事务包裹**：迁移可安全重复执行，整段在一个事务里，中断不留半成品。
5. **回归测试锁定**：`test_v040`、`test_admin_and_data_root`、`test_v030` 中的
   迁移用例（如 `test_v040_migration_adds_ai_columns_and_audit_table_idempotently`、
   `test_migration_backs_up_once_is_idempotent_and_preserves_history`）验证
   “旧库升级后历史数据完整保留、重复迁移不产生副作用”。

> 对数据盘的含义：迁移备份、完整备份也都写在数据根的 `snapshots/` 下，
> 只要数据根在数据盘，升级安全网同样落在数据盘。跨版本升级时，**先让新版本
> 在数据盘副本上跑一次迁移**（见第六节检查清单），确认 `quick_check=ok`
> 再切正式服务，可做到零风险。

## 一、确认设备与现状（两种形态都要先做）

```bash
# 1) 看清磁盘：确认 vda3 是未挂载的独立数据盘，而不是系统盘分区
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT
#   系统盘通常已挂在 /；数据盘 vda3 应无 MOUNTPOINT、无 FSTYPE（未格式化）

# 2) 确认 vda3 上没有需要的数据（新盘应无分区表/文件系统）
sudo blkid /dev/vda3 || echo "尚无文件系统，可安全格式化"

# 3) 记录当前服务数据根，后面要停服务
systemctl status jx-handover --no-pager   # 形态 A
# 或：cd deploy/cloud && docker compose ps # 形态 B
```

> ⚠️ 若 `lsblk` 显示 `vda3` 其实是系统盘 `vda` 上的分区且已用于 `/`，
> 说明设备名不是 vda3，请以 `lsblk` 实际输出为准替换下文所有 `/dev/vda3`。

## 二、格式化并挂载数据盘

```bash
# 1) 格式化为 ext4（会清空 vda3，确认无数据后再执行）
sudo mkfs.ext4 -L jx-data /dev/vda3

# 2) 建挂载点并挂载
sudo mkdir -p /data
sudo mount /dev/vda3 /data

# 3) 写入 /etc/fstab，用 UUID 避免设备名漂移导致开机挂载失败
UUID=$(sudo blkid -s UUID -o value /dev/vda3)
echo "UUID=${UUID}  /data  ext4  defaults,nofail  0  2" | sudo tee -a /etc/fstab

# 4) 验证 fstab 无误（这一步能防止重启后起不来，必须做）
sudo mount -a
df -h /data
```

`nofail` 保证即使这块盘异常，系统仍能启动，不会因为 fstab 挂载失败卡在开机。

## 三、形态 A：systemd 生产迁移

### 3.1 停服务并复制数据到新盘

```bash
sudo systemctl stop jx-handover

# 先让程序告诉你真实数据根在哪（0.5.3 起源码运行统一用 runtime，
# runtime-server 是历史目录，data_location.py 会指出当前生效的那个）：
python3 /www/wwwroot/jx_handover/backend/scripts/data_location.py

# 现有数据根（以上面输出为准）：/www/wwwroot/jx_handover/runtime 或 runtime-server
SRC=/www/wwwroot/jx_handover/runtime
DST=/data/jx-handover/data

sudo mkdir -p "$DST"
# -a 保留权限/时间戳；先复制不删除，旧目录留作回滚
sudo rsync -a "$SRC"/ "$DST"/

# 校验复制后的数据库完整性（quick_check 必须返回 ok）
# 注意子路径：数据库固定在 <数据根>/data/handover.db
sudo sqlite3 "$DST/data/handover.db" "PRAGMA quick_check;"
```

### 3.2 让服务指向新数据目录

应用读取环境变量 `JX_HANDOVER_DATA_DIR` 决定数据根，**显式配置时始终优先**，
不再随运行模式漂移。编辑服务器自己的 `.env`：

```bash
sudo vi /www/wwwroot/jx_handover/.env
```

加入（或修改）这一行：

```ini
JX_HANDOVER_DATA_DIR=/data/jx-handover/data
```

若服务是用 systemd unit 直接注入环境变量而非读 `.env`，则改 unit：

```bash
sudo systemctl edit jx-handover
# 在打开的 override 文件里写：
[Service]
Environment="JX_HANDOVER_DATA_DIR=/data/jx-handover/data"
```

### 3.3 目录属主与权限

服务以哪个用户跑就给哪个用户属主（宝塔环境常见 `www`，systemd 可能是专用
账户或 root）。先确认运行身份：

```bash
systemctl cat jx-handover | grep -E '^\s*User=' || echo "以 root 运行"
```

按运行身份授权（示例给 www；root 运行则 chown root:root）：

```bash
sudo chown -R www:www /data/jx-handover/data
sudo chmod 750 /data/jx-handover/data
```

### 3.4 启动并验证

```bash
sudo systemctl daemon-reload
sudo systemctl start jx-handover
journalctl -u jx-handover -n 40 --no-pager

# 健康检查应显示新数据根
curl -s http://127.0.0.1:8765/api/health | python3 -m json.tool
#   关注： "status":"ok", "data_root":"/data/jx-handover/data",
#          "database_journal_mode":"wal", "admin_configured":true

# 用仓库脚本再确认一次数据落点（源码在时可用）
python3 /www/wwwroot/jx_handover/backend/scripts/data_location.py
```

确认新库有数据后，旧目录**先保留几天**再删，不要立刻清理：

```bash
# 观察 1~2 天无异常后再执行
# sudo rm -rf /www/wwwroot/jx_handover/runtime-server
```

## 四、形态 B：Docker Compose 迁移

Docker 形态下容器内数据根固定为 `/var/lib/jx-handover`，由 compose 把宿主机
`JX_HOST_DATA_DIR` 绑定进去。**只需把 `JX_HOST_DATA_DIR` 指到新盘**，容器内
路径不用动。

```bash
cd /www/jx-handover/app/deploy/cloud   # 以实际 compose 目录为准

# 停容器
docker compose down

# 复制旧数据到新盘（旧 JX_HOST_DATA_DIR 常见为 /www/jx-handover/data）
sudo mkdir -p /data/jx-handover/data
sudo rsync -a /www/jx-handover/data/ /data/jx-handover/data/
sudo sqlite3 /data/jx-handover/data/data/handover.db "PRAGMA quick_check;"

# 改 .env 里的 JX_HOST_DATA_DIR
sudo vi .env
#   JX_HOST_DATA_DIR=/data/jx-handover/data
```

> 关键：`prepare-host.sh` 会把数据目录 chown 成容器运行身份 **UID/GID 10001**
> 并设 0750。手改路径后必须重跑它，否则容器（非 root）写不进新目录：

```bash
sudo bash deploy/cloud/scripts/prepare-host.sh   # 会按新 JX_HOST_DATA_DIR 建目录并授权
sudo bash deploy/cloud/scripts/deploy.sh          # 校验目录存在→compose 起服务
```

`deploy.sh` 在起服务前会检查 `JX_HOST_DATA_DIR` 目录存在，指向空盘会直接报错，
这是防呆，不是故障。验证同形态 A 的健康检查（`data_root` 在容器内显示为
`/var/lib/jx-handover`，对应宿主机新盘目录）。

## 五、宝塔面板 / 备份脚本 / 计划任务的访问

1. **宝塔面板**：面板以 root 运行，能访问 `/data`。若用宝塔的“文件”管理器
   查看，直接在路径栏输入 `/data/jx-handover/data` 即可；无需额外授权。
2. **OSS 异地备份脚本**：`backup-and-sync-oss.sh` 读取 `oss-backup.env` 里的
   `JX_HOST_DATA_DIR`，备份 ZIP 在 `${JX_HOST_DATA_DIR}/snapshots/full_backups`。
   迁移后必须同步改这个变量，否则脚本找不到备份目录：
   ```bash
   sudo vi /www/jx-handover/config/oss-backup.env
   #   JX_HOST_DATA_DIR=/data/jx-handover/data
   ```
   systemd 形态留空 `JX_CLOUD_COMPOSE_DIR`（应用内置调度器已自动生成每日备份，
   脚本只负责上传）。
3. **宝塔计划任务**：如果每日备份/上传是宝塔计划任务调度的 shell，确认任务里
   引用的路径已随 `oss-backup.env` 更新；执行用户需对 `/data` 有读写权（root
   或服务运行用户）。
4. **一键更新脚本** `/root/update_jx_handover.sh`：更新流程里的“备份运行数据”
   步骤若硬编码了旧 `runtime-server` 路径，需改为新数据根，或改为读取 `.env`
   的 `JX_HANDOVER_DATA_DIR`，避免更新时备份到空目录。

## 六、迁移后总检查清单

- [ ] `lsblk` 显示 `/dev/vda3` 挂在 `/data`，`/etc/fstab` 用 UUID 且含 `nofail`
- [ ] `sudo mount -a` 无报错（重启后能自动挂载）
- [ ] 服务已停时完成 rsync，`PRAGMA quick_check` 返回 `ok`
- [ ] `.env` / systemd override / compose `.env` 指向新数据根
- [ ] 目录属主=服务运行身份（形态 B 为 UID/GID 10001），权限 0750
- [ ] `/api/health`：`status=ok`、`data_root` 为新路径、`journal_mode=wal`、
      `admin_configured=true`
- [ ] `data_location.py` 输出新路径，且不再告警“存在含数据的历史目录”
- [ ] 管理页“完整业务备份”能在新盘生成一份并通过校验
- [ ] `oss-backup.env` 的 `JX_HOST_DATA_DIR` 已更新，手动跑一次备份脚本成功
- [ ] 观察 1~2 天确认无异常后，才删除旧数据目录

---

## 七、回滚

任一验证失败时：停服务 → 把 `.env`/override/compose 的数据根改回旧路径 →
起服务。因为迁移用的是 **复制而非移动**，旧目录仍在，可立即回退，无数据损失。
