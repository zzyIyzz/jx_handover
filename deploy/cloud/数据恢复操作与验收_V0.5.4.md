# V0.5.4 数据恢复操作与验收

## 先明确恢复范围

恢复不是合并：目标备份会替换数据库、imports 上传文件和 generated Word 文件。人员账号、密码、班次与审核状态回到备份时点，备份后的业务修改不会自动合入。服务器 .env、API Key 不从备份恢复。恢复后所有人须重新登录，使用备份时的账号密码；启动迁移仍会按服务器配置同步管理员。

应用必须是单实例、单 worker。先停止其他写入同一数据目录的程序，不支持在线热恢复或多个 worker 共享恢复任务。

## 首次升级本次恢复修复

如果旧系统已有“待恢复”任务，记下目标备份编号，在管理页取消旧任务后再运行 V0.5.4 更新脚本。新版脚本发现 pending.json 或 applying.json 会拒绝升级；applying.json 代表恢复进行中或中断，不能直接删除来绕过保护。

## 正常恢复

1. 在系统管理中确认当前数据根与目标备份的编号、时间、文件数；先创建并校验当前完整备份。
2. 点击目标备份“安排恢复”，确认替换范围，通知用户暂停录入。页面显示“尚未执行”才是准确状态。
3. 确认执行的是预期任务，再重启应用服务。当前默认 systemd 部署使用：

   ```bash
   sudo systemctl restart jx-handover
   sudo systemctl status jx-handover --no-pager
   sudo journalctl -u jx-handover -n 100 --no-pager
   ```

   服务名自定义时相应替换；Docker 应在原 Compose 目录重启 app；Windows 使用服务端控制器重启应用。不需要重启整台机器，不使用升级脚本来执行恢复。
4. 恢复在迁移和初始化数据库之前执行。系统复核备份摘要与数据根，制作恢复前完整备份，在暂存目录解压验证，再替换数据库和业务文件。
5. 重新登录并打开管理页，确认“上次恢复已完成”、目标备份编号、完成时间及恢复前备份编号。核对人员、班次、审核数据，打开历史 Word，抽查附件。接口健康不等于业务验收完成。

## 恢复失败

- 校验或准备失败：未替换业务数据，写入失败结果，清除失败待恢复任务并中止本次启动。systemd 若设置自动重启，可随后使用原数据启动。
- 替换阶段发生普通异常：尝试把原数据库与文件移回；回退成功后保留失败记录，下一次启动不重复恢复。
- 进程被杀、断电或自动回退失败：保留 applying.json、暂存和回滚目录，拒绝继续启动；绝不自动把现场当作成功恢复。程序自动恢复不能覆盖所有磁盘/硬件故障。

遇到最后一种情况：先停止服务，保存整个实际数据根、snapshots/restore 下的状态文件和日志。applying.json / last-result.json 中的 rollback_directory、staging_directory 和 pre_restore_backup_id 是人工核对依据。不要直接删除状态文件、覆盖在线数据库、单独混用旧数据库与新附件，或重复点击恢复。应在独立临时数据根验证完整的恢复前备份及文件一致性后，再制定停服回退步骤。

成功恢复保留的 .r 回滚目录不会自动清理。确认业务正确并有可用外部完整备份后，才由管理员安排清理。

## 保护边界

本次支持 Windows、Linux 单实例应用的启动恢复；本地测试包含正常恢复、摘要变化、错误目标目录、备份失败、替换失败、回退失败及中断重启阻断。实际服务器的磁盘空间、权限、服务环境变量和备份内容仍须现场验收。新恢复任务绑定数据根，旧任务缺少此字段时兼容执行，因此旧任务尤其要人工核对目录。
