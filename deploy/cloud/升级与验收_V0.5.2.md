# V0.5.2 升级与验收

公网入口仍是 `https://你的公网IP:1215`，内部服务仍是 `127.0.0.1:8765`。
本次不修改业务数据库结构、不重置个人密码。旧的浏览器 Cookie 不再用于个人账号登录，升级后每个人重新登录。

## 登录规则

- 姓名必须与启用人员账号完全一致。初始密码 `aaaa0000*` 仅适用于未修改过密码或管理员已重置的账号。
- 登录凭据只在当前页面内存保存，不进入 Cookie、localStorage 或 sessionStorage。
- 关闭、刷新、重新打开页面需要重新登录；页面内切换班次无需重复登录。
- 主动退出会使该账号其他设备的旧登录也失效；仅关闭页面不会影响其他人的使用。
- 登录后会调用 `/api/session/me` 验证身份。反向代理需要转发 `Authorization` 请求头（Nginx 默认转发）；不要在宝塔自定义规则里将它清空。
- 仍保留 HTTPS、来源地址校验、首次改密和失败次数限制。不要关闭安全校验来绕过报错。

## 升级已有 Docker 部署

先在管理页创建一份完整备份。管理员无法进入时，可在原 Compose 目录执行：

```bash
cd /www/jx-handover/app/deploy/cloud
docker compose exec -T app python -m scripts.cloud_backup create
```

确认备份成功后更新代码。若使用了其他项目路径，替换下列路径：

```bash
cd /www/jx-handover/app
git status --short
git pull --ff-only origin codex/v0.5.1-account-login
bash deploy/cloud/scripts/deploy.sh
```

若 Git 提示本地修改冲突，请保留修改并核对，不要执行强制覆盖。现有 `.env` 和 `oss-backup.env` 保持服务器自己的配置。
如果在配置中手工设置过 `JX_APP_VERSION`，更新为 `0.5.2` 或移除旧覆盖值。

## 已有 systemd / 宝塔 Python 部署

先确认服务名、项目目录、虚拟环境和正式数据目录，不要另开一套 Docker 服务同时访问数据库。

```bash
systemctl list-units --type=service --all --no-pager | grep -Ei 'jx|handover'
```

在原项目目录拉取同一分支，使用原虚拟环境安装 `backend/requirements.txt`；在 `frontend` 目录执行 `npm ci` 与 `npm run build`，然后在宝塔或 systemd 重启**原服务**。仅拉取源码不构建前端，页面仍会使用旧登录流程。

## 接入管理页 OSS 状态

服务器需要 Python 3 和 util-linux 中的 `flock`。新版脚本与 `oss-sync-receipt.py` 必须位于同一目录。

`deploy/cloud/oss-backup.env` 示例（实际值仅保存在服务器）：

```dotenv
# Docker 填原 Compose 目录；systemd 留空
JX_CLOUD_COMPOSE_DIR=/www/jx-handover/app/deploy/cloud
# 必须与正在运行的服务使用同一个正式数据根目录
JX_HOST_DATA_DIR=/www/jx-handover/data
JX_OSS_URI=oss://你的私有Bucket/jx-handover/production
JX_OSSUTIL_CONFIG=/www/jx-handover/config/ossutilconfig
JX_OSSUTIL_BIN=/usr/local/bin/ossutil
```

手动执行一次原同步任务：

```bash
bash /www/jx-handover/app/deploy/cloud/scripts/backup-and-sync-oss.sh
```

回执写到 `${JX_HOST_DATA_DIR}/snapshots/oss-sync-status.json`，容器和宿主机通过已有数据挂载共享。
管理页点击“刷新全部状态”即可读取。脚本不会把 AccessKey 或原始错误日志写入回执。
宝塔计划任务沿用该脚本，建议每日执行；26 小时未更新时页面显示过期，运行中超过 2 小时也提示检查任务。
没有备份、校验不通过、最近备份超过 36 小时或上传失败，任务返回非零并记录失败。
同步成功代表 OSS 工具完成备份包及清单上传；恢复可用性仍需要实际下载并恢复验证。

## 登录失败排查

1. `/api/health` 版本应为 `0.5.2`，`login_mode` 为 `account`；页面右上角也应显示 V0.5.2。不同版本说明后端未重启或前端未重新构建。
2. 姓名或密码错误：确认改名、停用和是否已修改初始密码；不要反复试默认密码。
3. “请求来源不一致”：核对 `.env` 的 `JX_PUBLIC_URL` 与浏览器地址是否完全一致，包含 `https://` 和 `:1215`。
4. 登录验证失败：检查 Nginx 是否转发 Authorization，以及前后端是否一起升级。
5. 429：按页面显示的等待时间重试。忘记密码由管理员重置；唯一管理员可在原虚拟环境或容器中运行 `python -m scripts.reset_staff_password '准确姓名'`。

## 现场验收

- 正确账号登录后能新建和编辑班次；错误密码有明确提示。
- 首次账号仍先改密；普通账号无法读取管理员诊断接口。
- 关闭后重新打开、刷新以及浏览器恢复页面均显示登录页；页面内切换班次保持登录。
- Word 生成、历史 Word 下载、XLSX 模板下载正常。
- 管理页显示 V0.5.2、真实备份时间；无 OSS 回执不会显示成功。
- 执行真实 OSS 上传后刷新管理页核对成功时间；失败时保留上次成功时间并明确提示当前失败。
- 在独立目录完成备份下载和恢复演练，确认历史 Word 与数据库数据可用。
