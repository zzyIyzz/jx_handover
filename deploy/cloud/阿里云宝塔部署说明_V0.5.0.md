# 江西片区智能交接班 V0.5.0 阿里云 ECS + 宝塔部署说明

## 1. 先说结论

这个系统可以部署到阿里云，但“云盘”需要拆成两个概念：

- 正在运行的唯一正式数据库：放在一台阿里云 ECS 的本地 ESSD 数据盘目录中。
- 异地备份：程序生成完整、可校验的 ZIP + JSON 后，再由 ECS 上传到私有 OSS。

不能把运行中的 `handover.db` 直接放进 OSS、NAS、SMB、WebDAV、同步盘或 FUSE 挂载目录。多人并不是共同打开一个数据库文件，而是共同访问同一个 HTTPS 网站，由一个后端进程顺序、安全地处理数据库读写。

推荐拓扑如下：

```text
使用人员浏览器
      │ HTTPS 443
      ▼
阿里云安全组 ── 只开放 80/443；SSH/宝塔只允许管理员 IP
      │
      ▼
宝塔 Nginx + SSL + 固定公网 IP 白名单或企业 VPN
      │ http://127.0.0.1:8765（仅 ECS 本机）
      ▼
Docker 单实例交接班系统
      │
      ├─ /www/jx-handover/data（ECS 本地 ESSD，唯一正式数据）
      └─ 已校验完整备份 ── ECS RAM 角色 ── 私有 OSS
```

V0.5.0 当前定位是“私有云部署测试版”。现有的“选择姓名 + 系统访问口令”适合固定办公出口 IP 或 VPN 后面的内部系统，不是面向任意公网用户的完整身份平台。不得删除 Nginx 白名单、把 443 放给所有来源后直接上线。如果确实要求人员在任何网络直接访问，必须先完成本文末尾所列的“个人账号/密码/MFA”升级。

部署前还必须把 GitHub 仓库设为 **Private**。既有 Git 历史包含内部场站和人员种子/演示信息，只删除当前分支中的文件不会清除旧提交；如需对外公开代码，应另行制作脱敏仓库或在完整备份、复核和明确授权后重写历史。本版没有把真实 `.env`、Qwen Key、数据库或实际工作日志加入 Git，但这不能替代对既有历史的治理。

## 2. 先确定访问方式

| 使用场景 | 入口控制 | 是否适合本版 | 说明 |
|---|---|---:|---|
| 所有人都从单位网络访问，单位有固定公网出口 IP | 阿里云安全组 + Nginx `allow/deny` | 是，首选 | 操作最简单，用户只需打开 HTTPS 域名 |
| 人员分散在不同地点，但可安装企业 VPN | VPN 网段白名单 + Nginx `allow/deny` | 是 | 安全性好，需先连 VPN |
| 人员用任意家庭网/手机网直接打开公网域名 | 个人账号、独立密码、找回/禁用、MFA | 否，需继续开发 | 共享访问口令不能承担公网身份认证 |

若目前还不能确定，先按“单位固定公网 IP 白名单”部署测试，不要先开放整个互联网再补安全。

## 3. 阿里云资源建议

以下是小团队单实例的工程估算，不是阿里云强制规格：

- ECS：2 vCPU、4 GiB 内存起步。
- 系统盘/数据盘：至少 80 GiB ESSD；正式使用前按历史 Word、Excel 和备份增长量调整。
- 操作系统：Ubuntu Server 22.04 LTS x86_64。
- 公网：固定公网 IP 或 EIP，3–5 Mbps 起步。
- 地域：优先选公司批准的中国内地地域并完成备案；没有备案且只做短期验证时，可评估中国香港地域，但必须先确认公司数据合规、跨地域和网络要求。
- 快照：给 ECS 数据盘配置自动快照。快照不能替代应用完整备份和 OSS 异地副本。

中国内地节点使用域名对外提供网站服务前需要完成 ICP 备案。阿里云备案说明：<https://help.aliyun.com/zh/icp-filing/basic-icp-service/user-guide/icp-filing-application-overview>。

## 4. 安全组与端口

先创建尽量小的安全组规则：

| 方向 | 协议/端口 | 来源 | 用途 |
|---|---|---|---|
| 入方向 | TCP 22 | 仅管理员固定公网 IP | SSH |
| 入方向 | 宝塔面板实际端口 | 仅管理员固定公网 IP | 宝塔管理；安装后修改默认端口 |
| 入方向 | TCP 80 | `0.0.0.0/0`，或按实际收紧 | 证书校验与跳转 HTTPS |
| 入方向 | TCP 443 | 最好直接限制为单位出口 IP/VPN；否则由 Nginx 二次限制 | 用户 HTTPS |
| 入方向 | TCP 8765 | 不创建规则 | 只允许 ECS 本机 Nginx 访问 |
| 入方向 | 3306、5432、6379 | 不创建规则 | 本版不对公网开放数据库/缓存 |
| 出方向 | TCP 443 | 按公司策略 | DashScope、OSS、软件更新 |

阿里云官方安全组建议把 Web 端口与后台管理端口分开控制，并让 SSH 只信任管理来源：

- <https://help.aliyun.com/zh/ecs/user-guide/start-using-security-groups>
- <https://help.aliyun.com/zh/ecs/user-guide/security-groups-for-different-use-cases>

部署后执行：

```bash
ss -lntp | grep 8765
```

正确结果只能看到宿主机 `127.0.0.1:8765`，不能看到宿主机 `0.0.0.0:8765`。容器内部监听 `0.0.0.0:8765` 是正常的，因为 Docker 只把它发布到宿主机回环地址。

## 5. 域名、备案与 SSL

1. 给系统准备独立子域名，例如 `handover.example.com`。
2. DNS A 记录指向 ECS 固定公网 IP/EIP。
3. 中国内地地域先完成 ICP 备案。
4. 宝塔“网站”中创建该域名的站点。
5. 宝塔“SSL”中申请并部署证书，开启强制 HTTPS。
6. 用户以后只访问 `https://handover.example.com`，不访问 IP，也不输入 `:8765`。

宝塔官方 SSL 操作说明：<https://docs.bt.cn/getting-started/deploy-ssl>。

## 6. 安装 Docker 并准备目录

在宝塔软件商店安装 Docker/Compose 管理器。宝塔也支持从 Compose 编排创建容器：

- <https://docs.bt.cn/api/docker/>
- <https://docs.bt.cn/user-guide/docker/website/docker-website-tutorial>

将本仓库放到稳定目录，推荐：

```text
/www/jx-handover/app       程序源码与部署文件
/www/jx-handover/data      唯一正式数据，ECS 本地 ESSD
/www/jx-handover/config    OSS RAM 角色配置
```

如果用 Git：

```bash
mkdir -p /www/jx-handover
cd /www/jx-handover
git clone https://github.com/zzyIyzz/jx_handover.git app
cd app
git switch codex/v0.5.0-aliyun-baota
```

然后执行：

```bash
cd /www/jx-handover/app
sudo bash deploy/cloud/scripts/prepare-host.sh
```

脚本只在 `.env` 不存在时创建示例配置，不覆盖已有口令或 Key；正式数据目录会设为容器用户 `10001:10001`、权限 `0750`。

## 7. 填写云端配置

编辑：

```text
/www/jx-handover/app/deploy/cloud/.env
```

至少修改：

```dotenv
JX_HOST_DATA_DIR=/www/jx-handover/data
JX_PUBLIC_URL=https://handover.example.com
JX_TRUSTED_HOSTS=handover.example.com,127.0.0.1,localhost
JX_CLOUD_ACCESS_SCOPE=private
JX_ACCESS_CODE=这里填写至少12位随机访问口令
JX_SESSION_SECRET=这里填写至少32位随机会话密钥
JX_ADMIN_NAMES=请填写实际管理员姓名
QWEN_API_KEY=这里填写你自己的DashScope_API_Key
```

可用 OpenSSL 生成随机值：

```bash
openssl rand -base64 24
openssl rand -hex 32
```

- 第一条可作为访问口令。
- 第二条可作为会话签名密钥。
- `.env` 权限保持 `0600`。
- 不要把 `.env`、截图中的 Key、完整访问口令发到 GitHub、群聊或反馈文档。
- Qwen Key 只在服务器容器环境中使用，不会进入前端构建产物。
- 阿里云百炼当前公布的模型调用 ID 为 `qwen3.8-flash`；开通地域、额度和计费以[官方模型页](https://help.aliyun.com/zh/model-studio/qwen3-8-flash)为准。
- 如果把 `JX_HOST_DATA_DIR` 改成自定义 ESSD 挂载目录，保存 `.env` 后要再次执行 `sudo bash deploy/cloud/scripts/prepare-host.sh`，由脚本创建目录并设置容器 UID/GID 权限。

云端入口会强制校验 HTTPS、访问口令长度、会话密钥长度、管理员、Secure Cookie、可信域名和私有访问声明；任一项不合格都会拒绝启动并给出明确错误。

## 8. 构建并启动

```bash
cd /www/jx-handover/app
bash deploy/cloud/scripts/deploy.sh
```

脚本会依次执行：

1. 校验 Compose 配置；
2. 构建 Vue 前端和 Python 后端镜像；
3. 启动一个且仅一个应用实例；
4. 轮询 `http://127.0.0.1:8765/api/health`；
5. 失败时显示最后 120 行容器日志。

常用命令：

```bash
cd /www/jx-handover/app/deploy/cloud
docker compose ps
docker compose logs --tail 200 app
docker compose restart app
docker compose stop app
docker compose up -d app
```

不要把 `--scale app=2`、多 worker 或第二套同数据目录的容器用于当前 SQLite 版本。本版明确是“一个容器、一个 Uvicorn worker、一个正式数据库”。

## 9. 宝塔 Nginx 反向代理与白名单

应用通过 Docker 只发布到 `127.0.0.1:8765`。宝塔站点把 HTTPS 请求反向代理到：

```text
http://127.0.0.1:8765
```

将 `deploy/cloud/nginx/jx-handover-location.conf.example` 中的内容合并到站点 HTTPS `server` 块，并把示例 IP 换成真实单位出口 IP 或 VPN 网段。优先保留宝塔生成的证书、ACME 校验和日志配置，不要用完整示例覆盖整个宝塔站点。保存前执行 `nginx -t`，通过后再重载。

宝塔反向代理说明：<https://docs.bt.cn/user-guide/site/php/site-config/reverse-proxy>。

注意：反向代理开启后，不要只依赖宝塔页面中另一个“访问限制”开关。白名单应明确写进实际生效的 Nginx `location /`：

```nginx
allow 你的单位固定公网IP;
# allow 你的VPN网段;
deny all;
proxy_pass http://127.0.0.1:8765;
```

如果使用 CDN，Nginx 看到的可能是 CDN 回源 IP，不能直接照搬以上白名单；必须先正确配置可信 `real_ip` 链路。初次部署建议不加 CDN。

示例会用 `$remote_addr` 覆盖浏览器自己发送的 `X-Forwarded-For`，保证应用审计和登录限流使用真实边界 IP。不要随意改回 `$proxy_add_x_forwarded_for`；只有在引入可信 CDN/SLB 并正确配置 `set_real_ip_from` 后才重新设计这条链路。

证书续期使用 HTTP-01 时，要保留宝塔生成的 `/.well-known/acme-challenge/` 例外；不能让业务 IP 白名单阻断 CA 校验。也可以按单位规范改用 DNS-01。

验收时必须做两次测试：

- 白名单内网络：能看到登录页并正常使用。
- 白名单外手机流量：返回 403，不能看到人员名单和登录页。

## 10. 配置 OSS 异地备份（推荐）

### 10.1 OSS Bucket

创建与 ECS 同地域的私有 Bucket，并配置：

- ACL：私有。
- 服务端加密：AES-256 或 KMS。
- 版本控制：开启。
- 生命周期：按公司要求保留，例如近期标准存储、长期低频；不要在恢复演练完成前设置过短删除周期。
- 不创建公共读链接，不把 Bucket 当网站目录。

阿里云 OSS 数据保护与加密说明：

- <https://help.aliyun.com/zh/oss/user-guide/data-encryption/>
- <https://help.aliyun.com/zh/oss/user-guide/data-protection-overview>

### 10.2 ECS RAM 角色

给 ECS 绑定专用实例 RAM 角色，仅授予目标 Bucket 前缀所需的 `ListObjects`、`GetObject`、`PutObject` 权限，不授予删除整个 Bucket 的权限，不在 ECS 保存长期 AccessKey。阿里云官方说明：<https://help.aliyun.com/zh/ecs/user-guide/attach-an-instance-ram-role-to-an-ecs-instance>。

### 10.3 安装并配置 ossutil

仓库脚本固定下载阿里云官方 ossutil 2.4.0 Linux x86_64 包并核对官方 SHA256：

```bash
cd /www/jx-handover/app
sudo bash deploy/cloud/scripts/install-ossutil.sh
```

复制配置：

```bash
cp deploy/cloud/ossutilconfig.example /www/jx-handover/config/ossutilconfig
chmod 600 /www/jx-handover/config/ossutilconfig
```

修改 `region` 和 `ecsRoleName`。示例使用 `Ali-EcsRamRole`（IMDSv2），不含 AK。阿里云 ossutil 官方说明：<https://help.aliyun.com/zh/oss/developer-reference/ossutil-overview/>。

再复制备份目标配置：

```bash
cp deploy/cloud/oss-backup.env.example deploy/cloud/oss-backup.env
chmod 600 deploy/cloud/oss-backup.env
```

修改 `JX_OSS_URI`、数据目录和角色配置路径，然后先测试：

```bash
ossutil -c /www/jx-handover/config/ossutilconfig ls oss://你的Bucket名称
bash deploy/cloud/scripts/backup-and-sync-oss.sh
```

脚本先让应用通过 SQLite 在线备份生成并校验完整 ZIP，再先上传 ZIP、最后上传 JSON 清单。看见远端 JSON 时，对应 ZIP 已上传完成。ossutil 自身使用 CRC64 校验和失败重试。

在宝塔“计划任务”中添加每天一次，例如 02:15：

```bash
cd /www/jx-handover/app && bash deploy/cloud/scripts/backup-and-sync-oss.sh >> /www/jx-handover/data/logs/oss-backup.log 2>&1
```

每月至少一次从 OSS 下载备份并实际恢复到测试目录，只有“上传成功但从未恢复”的备份不能视为已经验证的灾备。

### 10.4 从 OSS 取回一份备份

```bash
cd /www/jx-handover/app
sudo bash deploy/cloud/scripts/restore-backup-from-oss.sh 20260901-021500-a1b2c3d4
```

脚本下载 ZIP 和 JSON 后，会让容器执行 ZIP、全部文件 SHA256 与 SQLite `quick_check`。校验通过后，在网页“系统管理”中安排恢复，再执行：

```bash
cd /www/jx-handover/app/deploy/cloud
docker compose restart app
```

恢复发生在 Web 服务启动前；程序先自动生成恢复前留底备份，再替换正式数据。

## 11. 从现有 Windows V0.4.1 迁移到云端

1. 在 Windows 系统管理中创建一份“完整业务备份”。
2. 同时取得同编号的 `jx-handover-backup-*.zip` 和 `.json`，不要只复制数据库文件。
3. 先在 ECS 启动一个空系统并确认管理员可登录。
4. 把 ZIP + JSON 上传到：

   ```text
   /www/jx-handover/data/snapshots/full_backups
   ```

5. 修正权限：

   ```bash
   chown 10001:10001 /www/jx-handover/data/snapshots/full_backups/jx-handover-backup-*
   chmod 640 /www/jx-handover/data/snapshots/full_backups/jx-handover-backup-*
   ```

6. 网页“系统管理”中重新校验该备份、安排恢复。
7. `docker compose restart app`。
8. 检查班次、导入原件、历史 Word 和生成路径。V0.5.0 已处理 Windows 反斜杠路径迁移到 Linux 的重写。
9. Qwen Key、访问口令和会话密钥不会进入业务备份，必须在新服务器 `.env` 中重新配置。

迁移完成前保留原 Windows 服务器和原完整备份，不要立即删除或覆盖。

## 12. 自定义正式数据地址

正常首次部署只需修改 `.env` 中：

```dotenv
JX_HOST_DATA_DIR=/你选择的ECS本地ESSD目录
```

如果已有数据后需要换盘：

1. 创建网页完整备份并同步 OSS。
2. `docker compose stop app`。
3. 用 `rsync -aHAX` 把旧目录完整复制到新 ECS 本地盘。
4. 新目录设为 `10001:10001`、权限 `0750`。
5. 修改 `.env` 的 `JX_HOST_DATA_DIR`。
6. 再执行 `sudo bash deploy/cloud/scripts/prepare-host.sh` 复核并准备新目录。
7. `docker compose up -d app`。
8. 检查健康、历史 Word、生成 Word和备份。
9. 验收完成前不要删除旧目录。

只允许本地 ESSD 路径。即使 OSS/NAS 被挂载成一个 Linux 目录，也不能把它填成正式数据根目录。

## 13. 升级与回滚

升级前：

1. 网页创建完整备份；
2. 确认 OSS 同步完成；
3. 记录当前 Git 提交和镜像 ID；
4. 再拉取新版本并重建。

示例：

```bash
cd /www/jx-handover/app
git fetch origin
git switch codex/v0.5.0-aliyun-baota
git pull --ff-only
bash deploy/cloud/scripts/deploy.sh
```

代码和数据分离：重建/替换容器不会覆盖 `/www/jx-handover/data`。但如果新版本含数据库迁移，回滚代码前必须阅读对应升级说明，不能默认旧代码一定认识新结构。

## 14. 现场最低验收门槛

以下全部通过后，才算“云端可试用”：

- 宿主机只在 `127.0.0.1:8765` 监听应用端口。
- 白名单外网络不能看到系统。
- HTTPS 证书有效，HTTP 自动跳 HTTPS。
- 两台以上电脑同时编辑时，乐观锁冲突能提示而不是静默覆盖。
- 实际工作日志 Excel 可预览、确认导入、重复确认不重复写入。
- 六章 Word 生成、下载、历史版本均正常。
- Qwen 连通测试成功；断网/Key 错误时能回退本地规则。
- 创建完整备份、上传 OSS、下载、校验、恢复演练全部通过。
- ECS 重启后容器自动恢复，数据库、导入原件和历史 Word 都还在。
- `.env`、Qwen Key、访问口令和会话密钥没有进入 Git 或反馈材料。

逐项记录请使用同目录的《云端现场验收与反馈清单_V0.5.0.md》。
